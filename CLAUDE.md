## Перевірка тверджень — ланцюг "гіпотеза → теорія → теорема → доказ"

Кожне твердження у paper'і повинне пройти повний ланцюг:

1. **Гіпотеза**: чітко сформульована, фальсифікована, з областю застосовності
2. **Теорія**: контекст у літературі, з посиланнями на класичні роботи (Shannon,
   Slepian-Wolf, Cover-Thomas, Watanabe, Charikar et al., Wagner-Corneil etc.)
3. **Теорема (формальне твердження)**: точна, без двозначностей, з явними
   передумовами
4. **Доказ**: повний, без "easy to see" чи "obviously"; кожен крок або
   класичний результат з цитатою, або виведений з попередніх кроків

Якщо хоча б один елемент ланцюга слабкий — теорема НЕ готова.

## Декомпозиція великих кроків

Якщо доказ не йде як одна теорема — **розбивай на проміжні леми**, кожна з яких
доказується повністю з опорою на попередні. Не намагайся протягти один великий
крок через хибне посилання на "загальний результат".

Приклад успішної декомпозиції: Theorem 4.3 (декомпозиція через діалог codex,
3 раунди, остаточна структура — Remark 4.3a + Theorem 4.3 + Remark 4.3b
використовуючи Wagner-Corneil 1990 редукцію замість зламаного QAP-Hamming
hand-wave).

## Практична верифікація — кожен крок як робоча програма

Кожна теорема, лема, пропозиція повинна мати **виконувану перевірку** у
`scripts/verify/` або `tests/`. Форма залежить від типу твердження:

- **Конструктивні теореми** (Thm 5.4 існує лінійний код з P1/P2/P3): скрипт
  будує об'єкт випадково, перевіряє властивості, демонструє розрив
- **Алгоритмічні (NP-hardness)** (Thm 4.3, 6.7): скрипт реалізує редукцію для
  невеликого випадку і перевіряє правильність відображення YES/NO інстансів
- **Тотожності** (Thm 5.5 TC = sum H_marg - H_joint): скрипт обчислює обидві
  частини для випадкових малих розподілів і перевіряє рівність
- **Контрприклади** (Prop 5.7 був зламаний контрприкладом N=7,k=2,s=2):
  Python-скрипт codex'а, який знайшов контрприклад, — це і є практична
  перевірка
- **Граничні випадки**: малі N значення, виродженні розподіли, edge cases

Структура `scripts/verify/`:
- один файл на теорему: `thm_5_4_linear_code_separation.py`
- виводити PASS/FAIL у stdout
- бути включеним у CI як окремий job (зелений CI = усі формальні і виконувані
  перевірки пройшли)

## Adversarial review з codex

Workflow для нових теорем або реверифікації існуючих:

1. **Codex як адверсар**: попроси codex намагатися довести теорему НЕВІРНОЮ.
   Прохання типу "review and find issues" дає слабкі відповіді — потрібно
   "PROVE wrong, with counterexample, citation error, missing case, or proof
   gap. If you fail honestly, say 'Attack failed; result holds'."
2. **Codex використовує web search** для перевірки цитат: Wagner-Corneil 1990,
   Charikar et al. 2005, Cover-Thomas, Watanabe 1960 тощо. Це критично — у
   попередньому раунді codex знайшов мою власну помилку в цитуванні Charikar.
3. **Дій 1 секція за раз** (§3-4, §5, §6, §7-9, §10). Великий промпт мовчки
   падає; chunked працює.

## Протокол після фіксу — три кроки

Кожна теорема після виправлень (codex repair → застосування → компіляція →
коміт) НЕ вважається повністю довеленою, поки не пройде усі три:

1. **Холодне re-review мною (Claude)**: прочитай теорему і доведення ще раз
   власними очима, без покладання на codex'ові висновки. Спробуй знайти
   логічні розриви, неявні припущення, неправильні референції. Якщо знайшов —
   виправ і повтори.

2. **Холодне re-review codex'ом**: окремий запит до codex з ясною інструкцією
   "post-fix re-review of [X]; for each prior concern report status RESOLVED /
   PARTIAL / UNRESOLVED / NEW (різні проблеми введені)". Без посилань на мої
   власні висновки — codex має судити незалежно.

3. **Adversarial disprove codex'ом**: окремий запит "PROVE the (fixed)
   theorem is still wrong: construct a counterexample, find a missing case,
   identify a citation error. If you fail honestly, say 'Attack failed;
   theorem holds'." Кожна "RESOLVED" з кроку (2) має ще пройти "Attack failed"
   з кроку (3).

Якщо будь-який з трьох кроків знаходить новий issue — повертаємось до циклу
codex repair. Не переходимо до наступної теореми, поки всі три цикли не дали
"clean / Attack failed" для поточної.

## Дискусія, не покора

Не приймай висновок codex без критичної оцінки. Якщо є сумнів — заперечуй.

- Codex може помилятися у деталях редукції — перевір математику самостійно
- Я (Claude) можу мати упередження від попередніх раундів — критично читай
  codex'ове заперечення
- Truth > перемога в суперечці. Якщо codex дає чесну контраргументацію — приймай
- Якщо я даю чесну контраргументацію — codex прийме

Прикладі успішних діалогів:
- Theorem 4.3 decomposition: 3 раунди, на 2-му я зловив три моменти (Wagner-
  Corneil точність, асиметричність F, відсутність APX-hardness), codex
  підтвердив усі три з web search, і запропонував чистіше рішення для (2)
- Theorem 6.8 Charikar attribution: моя власна попередня "виправлення"
  (Ω(log n / log log n) via Lund-Yannakakis) була НЕВІРНА — codex's web search
  виявив правильний бонд 8569/8568, який я мусив прийняти

## Waterfall, не Kanban

Для теоретичної роботи де кожен крок залежить від валідованих попередніх —
waterfall:

- Завершити повністю одну теорему (review → діалог → застосування → компіляція
  → коміт → CI зелений) до переходу до наступної
- Не паралелити декілька теорем одночасно
- Не починати наступну, поки попередня не закінчена цілком

## Маленькі чесні кроки, не великі стрибки

Якщо є невпевненість — менший крок з чесним кінцевим результатом краще, ніж
великий стрибок з прихованими гіпотезами. Краще "weakened theorem holds" ніж
"strong theorem with hand-wave".

## Розширення scope перевірки

Не обмежуватись лише numbered theorems. Перевіряти також:

- **§1 Motivation і Hypothesis**: чи кожна "ми вважаємо що" / "це означає, що"
  / "практичний приклад показує" — підкріплена доказом або явно позначена як
  conjecture?
- **§2 Preliminaries**: чи цитати на класичні результати (Slepian-Wolf, MDL,
  bits-back) точні? Чи формулювання матчить оригінали?
- **§11 Experimental predictions**: чи кожне числове передбачення (наприклад
  "1.5-2.0 bpb on enwik9") підкріплене аргументом, що зв'язує його з теорією?
- **§12 Related work**: чи всі цитати читабельні, чи характеризації методів
  правильні?
- **§13 Open problems**: чи кожна "open" проблема справді не вирішена, чи
  існує відомий результат, який я пропускаю?

## Коли НЕ застосовувати

Ці правила — для math/theory роботи в RNR. Для звичайних кодових задач
(нескладні баг-фікси, рутинні рефакторинги) waterfall занадто дорогий — там
норма "fix → compile → push → next".
